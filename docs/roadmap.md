### 与最初草案的差异(逐条记录,不粉饰)

### 保留的机制

1. **允许清单**:只有表里的路径能被删;输入不在表里,写错也删不到。
2. **逐条复核**(删除前一刻再做一次):相对路径、无 `..`、非软链接、父目录 relpath 在仓库内、不是申报输入。
3. **前后盘点**:`data/raw|db|reference` 的文件数与 KiB、`git` 被跟踪文件数量与修改数,清理前后各记一次并 `diff`;不符即 exit 1 并打印差异。
4. **口径**:释放量用 `df` 前后差;`du` 数字标注"上界"。
5. **拒绝**:运行中的 Nextflow、软链接的 `results/`(否则 `work/` 可能是唯一副本)、非终端且无 `--yes`(exit 2,不猜)。

### 负对照(证明守卫真的会拦)

- 无 `--yes` + 非终端 → exit 2,一个字节都没动;
- `results/` 是软链接 → exit 1,软链接目标文件完好;
- 把 `data/raw` 注入**副本**的删除表 → 仍被"申报输入"拒掉(允许清单不是最后一道防线)。

### 遗留

- `pgrep` 分支在本机沙箱内无法实测(`ps`/`pgrep` 被沙箱禁止),CI 与正常终端上可执行。
- 故意不做扩权开关(`--include-db` 之类):4 GB 参考库重建要重新下载,**不给这个按钮**。
- **成本**:约半天(含测试)—— 实际约 1.5 小时(含两条 `-resume` 实测)。

## C. 本地一键 UI(先做 MVP,决策待定)

**定位**:本地单用户界面,**不是公网服务**。理由已论证:4 GB 参考库谁维护、8 核算力谁付、病原数据合规谁承担 —— 这三问答不出来,公网服务三年内必死(参考 BV-BRC / KBase 这类国家经费平台已占位)。

**MVP 范围(约 2 天)**:

```
选文件(给路径,不上传) → 写 samples.tsv → 启动一次 nextflow run .
   → SSE 实时日志 → 跑完把 results/report/multiqc_report.html 嵌进 iframe
   → 一键下载整个 results/
```

**关键约束**:

- **一次只跑一个任务** —— 与"单一输出根"的约定一致,省掉全部并发问题;
- 文件从本地文件系统选取,**不经浏览器上传**(400 MB 的 FASTQ 上传是这一步最容易做失败的地方,而本地服务根本不需要);
- 复用现成产物:报告已经是单文件自包含(15 MB),UI 不需要新的展示层。

**明确不做**:账号、多用户、配额、HPC、云端、多引擎。

**前置依赖**:A(清空)与 B(一次无人值守的成功重跑)。UI 的价值取决于"从零到报告"能不能稳定跑通,而不是取决于界面好不好看。

**验收**:一个没装过任何环境的同事,从选两个 FASTQ 到看见报告 ≤ 45 分钟;失败时界面能指出**是哪一步、为什么**,而不是白屏或一个绿勾。

**成本**:约 2 天(含一个下午的健壮性:取消、磁盘检查、错误呈现)。

## 为什么按这个顺序

`A → B → C`。清空让重跑变成零成本动作;重跑证明"从零到报告"是可靠的;UI 只是给这条已经可靠的路径套一层壳。反过来做(先做 UI)会在一个还没有验证过的地基上盖房子。
